-- ============================================================================
-- 第 1 章: 统一键命名规范
-- ============================================================================
-- 
-- 命名空间层级:
--   sgp:{domain}:{entity}:{qualifier}
--     |      |         |
--     |      |         +-- 限定符 (版本号、用户 ID、窗口标识等)
--     |      +-- 实体 (具体缓存对象)
--     +-- 域 (业务领域)
--
-- 命名规则:
--   1. 全部小写字母 + 数字 + 下划线
--   2. 分隔符统一为冒号 (:)
--   3. 禁止特殊字符 (@, #, %, &, 空格)
--   4. 版本号格式: v{正整数} (如 v1, v7, v42)
--   5. 通配符: * 用于 SCAN 匹配 (如 sgp:graph:*)
--
-- 8 大域分类:
--   graph    — 图计算缓存 (算法结果, 拓扑数据, 统计摘要)
--   auth     — 认证授权缓存 (Token 黑名单, API Key 验证, Token Family)
--   rate     — 限流计数器 (滑动窗口 Sorted Set, 固定窗口计数器)
--   lock     — 分布式锁 (计算锁, 资源锁)
--   session  — 用户会话 (设备列表, Refresh Token 家族)
--   pubsub   — 发布/订阅频道 (缓存失效广播, 算法进度, 系统事件, 协同)
--   metrics  — 实时指标 (缓存命中率, 连接池状态, 性能采样)
--   config   — 动态配置 (功能开关, 限流阈值, 维护模式)
--
-- ============================================================================

-- ============================================================================
-- 第 3 章: 版本管理策略
-- ============================================================================
--
-- 3.1 数据版本号 (Data Version)
--   键: sgp:meta:data_version:{domain}
--   类型: String (整数, 从 1 开始)
--   变更: INCR (数据更新时自增)
--   用途: 版本号嵌入缓存键中，实现"软失效"
--
-- 3.2 版本传播流程:
--   1. 数据导入完成 (Neo4j 写入 / C++ 引擎计算完成)
--   2. INCR sgp:meta:data_version:graph    (如: 7 → 8)
--   3. 新请求自动生成新版本键:             sgp:graph:pagerank:v8
--   4. 旧版本键 v7 保持不变，靠 TTL 自然过期 (24h)
--   5. 零删除操作，无时钟风暴
--
-- 3.3 何时递增版本:
--   - 新数据导入 (facebook_combined.txt 更新)
--   - 手动触发全部算法重新计算
--   - 数据修复/迁移完成
--
-- 3.4 版本号获取:
--   ver = await get_data_version("graph")
--   cache_key = f"sgp:graph:pagerank:v{ver}"
--
-- 3.5 版本号注意事项:
--   - 全局单调递增 (INCR 保证)
--   - 不可回退 (即使数据回滚，版本号继续递增)
--   - 旧版本键占用内存直到 TTL 过期 (通常 < 24h，在预计内存 < 10MB 内可接受)
-- ============================================================================


-- ============================================================================
-- 第 4 章: TTL 策略体系
-- ============================================================================
--
-- 4.1 TTL 层级 (Data-Driven Tiers)
-- ┌─────────────┬──────────────┬────────────────────────────────┬───────────────────────────────────────────┐
-- │ Tier        │ TTL 范围     │ 数据类型                       │ 理由                                      │
-- ├─────────────┼──────────────┼────────────────────────────────┼───────────────────────────────────────────┤
-- │ Hot         │ 30-600s      │ 实时统计, 限流窗口, 分布式锁  │ 频繁变化, 短 TTL 保证数据新鲜度           │
-- │ Warm        │ 1800-7200s   │ 拓扑数据, 会话列表, API Key   │ 偶尔变化, 中等 TTL 平衡命中率和一致性     │
-- │ Stable      │ 43200-172800s│ 算法结果 (静态图)             │ 极少变化 (静态数据), 长 TTL 最大化命中率  │
-- │ Persistent  │ 604800-2592000s│ 用户偏好, 动态配置          │ 手动失效, 年尺度 TTL [1]                  │
-- └─────────────┴──────────────┴────────────────────────────────┴───────────────────────────────────────────┘
-- [1] Persistent 键实际靠手动失效管理，TTL 仅作兜底安全网。
--
-- 4.2 TTL Jitter (缓存雪崩防护)
--   问题: 大量缓存键同时创建 → 同时过期 → 流量全部打中后端
--   方案: 每条键在 base_ttl 上添加 ±10% 随机偏移
--   实现:
--     import random
--     jitter = int(base_ttl * 0.10)
--     ttl = base_ttl + random.randint(0, jitter)
--   覆盖: cache_get_or_compute() 自动应用，无需调用方关心。
--
-- 4.3 TTL by Access Pattern
--   ┌──────────────────────┬──────────────────────────────────────┐
--   │ 访问模式             │ TTL 策略                             │
--   ├──────────────────────┼──────────────────────────────────────┤
--   │ 读多, 写极少         │ 长 TTL + 主动刷新 (warm_cache)      │
--   │ 读多, 写频繁         │ 短 TTL + Write-Through              │
--   │ 写为主               │ Cache-Aside + 写入即失效             │
--   │ 不缓存               │ Path queries (组合爆炸, 0 收益)     │
--   └──────────────────────┴──────────────────────────────────────┘
--
-- 4.4 缓存预热优先级
--   ┌──────┬───────────────────┬───────────────────────────────────┐
--   │ 优先级│ 内容              │ 触发时机                          │
--   ├──────┼───────────────────┼───────────────────────────────────┤
--   │ P0   │ Topology, Stats   │ 应用启动时 (lifespan startup)    │
--   │ P1   │ 所有算法结果      │ 首次请求时 (Cache-Aside 懒加载)  │
--   │ P2   │ Path queries      │ 不预热 (组合爆炸, 按需计算)      │
--   └──────┴───────────────────┴───────────────────────────────────┘
-- ============================================================================


-- ============================================================================
-- 第 5 章: 5 种缓存失效模式
-- ============================================================================

-- ═══════════════════════════════════════════════════════════════
-- 模式 1: 版本失效 (Version-Based) — 主要策略
-- ═══════════════════════════════════════════════════════════════
-- 原理:
--   - 数据版本号存储在 sgp:meta:data_version:{domain}
--   - 缓存键包含版本: sgp:graph:pagerank:v{ver}
--   - 数据变更时 INCR 版本号
--   - 新请求自动使用新版本键，旧版本键靠 TTL 自然过期
-- 优势:
--   - 零删除操作，无 SCAN 阻塞
--   - 所有 Worker 自动感知（因为版本号存储在 Redis 中）
-- 劣势:
--   - 旧版本缓存占用内存直到 TTL 过期
-- 适用:
--   - 图数据更新 (数据导入后)
--   - 全量算法重算

-- ═══════════════════════════════════════════════════════════════
-- 模式 2: 标签失效 (Tag-Based)
-- ═══════════════════════════════════════════════════════════════
-- 原理:
--   - 标签存储在 sgp:tag:{tag} (Set 类型)
--   - 写入缓存时注册关联: SADD sgp:tag:pagerank sgp:graph:pagerank:v3
--   - 失效时: SMEMBERS sgp:tag:pagerank → DELETE 所有关联键
-- 优势:
--   - 精确删除，不漏删也不多删
--   - 跨版本、跨键模式批量操作
-- 劣势:
--   - 需要维护标签 Set (但 Redis Set 开销极小)
-- 适用:
--   - 特定算法重算后 (失效该算法所有版本的缓存)
--   - 用户数据变更后 (失效该用户的所有相关缓存)

-- ═══════════════════════════════════════════════════════════════
-- 模式 3: TTL 失效 (Time-Based) — 兜底策略
-- ═══════════════════════════════════════════════════════════════
-- 原理:
--   - 每条缓存键在 SETEX 时指定过期时间
--   - TTL 作为安全网，即使前两种模式都失效，键也会自动过期
-- 优势:
--   - 零维护成本，Redis 内核自动清理
--   - 防止内存泄漏的最后防线
-- 劣势:
--   - 无法精确控制时效时机
-- 适用:
--   - 所有缓存键的默认安全网

-- ═══════════════════════════════════════════════════════════════
-- 模式 4: 事件驱动失效 (Pub/Sub Broadcast)
-- ═══════════════════════════════════════════════════════════════
-- 原理:
--   - Admin API 失效缓存时，发布消息到 sgp:pubsub:cache-invalid
--   - 所有 FastAPI Worker 订阅该频道，收到消息后执行本地缓存失效
-- 优势:
--   - 多进程/多实例缓存一致性
--   - 实时性高 (毫秒级)
-- 劣势:
--   - 需要 Pub/Sub 基础设施
--   - 消息不持久化 (Redis Pub/Sub 是 fire-and-forget)
-- 适用:
--   - 多 Worker 部署场景
--   - 手动管理操作需要立即在所有实例生效

-- ═══════════════════════════════════════════════════════════════
-- 模式 5: 手动/管理失效 (Admin API)
-- ═══════════════════════════════════════════════════════════════
-- 原理:
--   - Admin API: POST /api/v1/admin/cache/invalidate?pattern=...
--   - SCAN 匹配模式 → 批量 DELETE
-- 安全限制:
--   - 禁止 pattern="*" (防止误删所有键)
--   - 禁止 pattern="sgp:*" (生产环境额外限制)
--   - 支持域缩写: pattern="graph" → 展开为 "sgp:graph:*"
-- 适用:
--   - 运维排障时需要立即清除某类缓存
--   - 调试/测试环境快速重置
-- ============================================================================

-- ============================================================================
-- 第 8 章: 缓存穿透 / 击穿 / 雪崩 防护
-- ============================================================================
--
-- 8.1 缓存穿透 (查询不存在的数据)
--   攻击场景: 查询 node_id=99999999 (不存在), 每次穿透缓存打中 Neo4j/C++ 引擎
--   防护方案:
--     a. 缓存空值 (NULL marker "__CACHE_NULL__"), TTL=60s
--        SET sgp:graph:node:99999999 "__CACHE_NULL__" EX 60
--     b. 布隆过滤器 (可选, 大规模部署时推荐)
--        预先将所有合法 node_id 写入 Bloom Filter
--        查询前先检查 Bloom Filter, 不存在直接拒绝
--        当前数据量 (4K 节点) 不需要, 后续扩展到 10M+ 时启用
--
-- 8.2 缓存击穿 (热点 key 过期瞬间)
--   场景: topology:v7 过期瞬间, 10 个用户同时刷新 → 10 次 Neo4j 查询
--   防护方案 (多层):
--     a. 分布式锁: SET NX EX 30, 只有一个请求执行计算, 其余等待
--     b. 永不过期 (逻辑上): 异步刷新 + 分布式锁, 保证始终有值
--     c. 熔断降级: 3 次计算超时 → 自动返回上一次的过期缓存值
--   当前实现: 方案 a (分布式锁), 方案 b 待实现
--
-- 8.3 缓存雪崩 (大量 key 同时过期)
--   场景: 所有算法结果 TTL 均为 86400, 同时写入, 同时过期
--   防护方案:
--     a. TTL Jitter: ±10% 随机偏移 (已实现)
--     b. 错峰创建: 各算法结果在首次请求时独立创建 (当前状态)
--     c. 多级缓存: Redis → 本地内存 → 降级兜底 (后续规划)
--   当前风险: 低 — 算法结果创建时间天然分散 (懒加载)
--   未来风险: 如果改为启动时批量预热, 需要确保 jitter 已启用
