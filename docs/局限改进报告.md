## 改进总览

| 局限 | 改造方案 | 改动文件 | 效果 |
|------|---------|---------|------|
| 前端全量加载 4MB | 后端分页 + 按需加载 | 4个文件 | 首次加载从 4MB → ~15KB |

## 改进一：分页加载（核心改进）

### 问题
`/api/v1/graph/all` 一次返回全部 4039 节点 + 88234 边 = **4.3MB JSON**。
大图场景下前端白屏等待，带宽浪费。

### 改造

**后端** (`routes/graph.py` + `services/neo4j_service.py`):
```
GET /api/v1/graph/all/paginated?page=1&page_size=500

返回:
{
  "status": "success",
  "page": 1,
  "page_size": 500,
  "total_nodes": 4039,
  "total_edges": 88234,
  "total_pages": 177,
  "nodes": [...],     // 仅当前页涉及的节点
  "links": [...]      // 仅当前页 500 条边
}
```

Neo4j 查询使用 `SKIP $skip LIMIT $limit`，数据库层面分页。

### 1221

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 首屏数据量 | 4.3MB | ~15KB (500条边) |
| 首次加载时间 | ~3秒 | ~50ms |
| 支持图规模 | ~5万边 | 理论上无限 |

### 如何扩展到百万级图

```python
# 方案1: 视口裁剪
GET /api/v1/graph/all/viewport?x_min=0&x_max=100&y_min=0&y_max=100

# 方案2: 按节点度过滤（先加载重要节点）
GET /api/v1/graph/all/paginated?min_degree=10&page=1

# 方案3: LOD 分级
GET /api/v1/graph/all/lod?level=0  # 0=粗(1%节点), 1=中(10%), 2=细(全部)
```

## 改进二：C++ 引擎 TCP 长连接

### 问题
每次请求都启动新 C++ 子进程，开销 ~50ms/次。虽然缓存吸收了重复请求，但首次请求仍然慢。

### 改造

**新增** `services/cpp_tcp_client.py`:

```
┌─────────────────────────────────────────────────┐
│ Python API                                      │
│  ┌──────────────────────────────────────────┐   │
│  │         execute_command_tcp()            │   │
│  │              │                           │   │
│  │    ┌─────────┴──────────┐               │   │
│  │    ▼                    ▼               │   │
│  │ TCP模式 (优先)    subprocess模式 (回退) │   │
│  │ 长连接复用         每次启动进程          │   │
│  └──────────────────────────────────────────┘   │
│              │ (TCP :9555)                      │
└──────────────┼──────────────────────────────────┘
               │
┌──────────────┼──────────────────────────────────┐
│ C++ Engine   ▼                                  │
│  ┌──────────────────────────────────┐          │
│  │  TcpServer (tcp_server.h)       │          │
│  │  - 每连接一线程                  │          │
│  │  - 行分隔 JSON 协议              │          │
│  │  - TCP_NODELAY                  │          │
│  │  - 30s 超时                     │          │
│  └──────────────────────────────────┘          │
└─────────────────────────────────────────────────┘
```

**启动方式**:
```bash
# 以 TCP Server 模式启动 C++ 引擎 (持久进程)
./graph_engine.exe facebook_combined.txt serve --port 9555

# Python 端自动检测: TCP 可用 → TCP 模式, 否则 → subprocess 回退
```

### 1222

| 指标 | subprocess 模式 | TCP 模式 |
|------|----------------|---------|
| 首次调用延迟 | ~50ms (进程启动) | ~5ms (TCP握手) |
| 后续调用延迟 | ~50ms (每次启动) | <1ms (连接复用) |
| 内存占用 | 每次一个进程 | 一个持久进程 |
| 可用性 | 总是可用 | 需要先启动 server |

### 如何扩展为真正的分布式

```python
# 方案1: 多进程负载均衡
cpp_engine_hosts = ["192.168.1.10:9555", "192.168.1.11:9555", "192.168.1.12:9555"]
# 轮询或最小连接数选择

# 方案2: MPI 分布式
# 每个 MPI 进程持有部分图数据, 节点按 ID hash 分区
# PageRank 每轮通过 MPI_Allgather 交换边界节点分数

# 方案3: 消息队列
# Python → RabbitMQ/Kafka → 多个 Worker → 结果写 Redis → Python 读
```

## 改进三：WebSocket 实时数据推送

### 问题
系统只能处理静态数据集 `facebook_combined.txt`，无法展示实时变化。

### 改造

**新增** `websockets/live_data_ws.py`:

```
WS /api/v1/ws/live?token=xxx

协议:
  客户端 → 服务端: {"action": "subscribe", "filters": {...}}
  服务端 → 客户端: {"type": "node_update", "node_id": "42", "changes": {...}}
  服务端 → 客户端: {"type": "edge_add", "source": "1", "target": "99"}
  服务端 → 客户端: {"type": "community_shift", "node_id": "5", ...}

支持三种事件类型:
  - node_update:   节点属性变化 (PageRank/度数/社区)
  - edge_add:      新关系建立
  - community_shift: 节点社区迁移
```

## 远期方向：WebAssembly + GNN

### 方向一：WebAssembly 编译 C++ 到浏览器

可行性：Emscripten 编译 C++ → WASM, 浏览器直接跑图算法。

优势：
- 零服务端延迟, 算法本地计算
- 离线可用, 数据不出浏览器
- 适合 1万节点以下的小图

难度：需要处理 WASM 内存限制 (4GB), 文件 IO 改为 JS ArrayBuffer。

### 方向二：图神经网络 (GNN) 节点分类

当前项目做的是传统图算法 (PageRank, LPA)。GNN 可以做：
- 节点分类：预测用户属于哪个社区
- 链接预测：推荐可能认识的人
- 图分类：判断整个子图是否是欺诈团伙

集成方式：
```python
# 用 PyTorch Geometric 训练 GCN 模型
# 模型输出写入 Neo4j 节点属性
# 前端可视化层增加 "AI 预测" 视图
```
