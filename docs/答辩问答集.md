## 一、系统架构类

### ⭐ Q1: 你的系统整体架构是怎样的？
```
三层架构:
前端(WebGL 3D可视化) → 中间层(FastAPI网关) → 底层(C++引擎+数据库)

前端用 ES6 原生模块 + 3d-force-graph 库做 3D 力导向图渲染。
中间层是 FastAPI 异步框架, 5层中间件链, 37个API端点。
底层 C++ 引擎实现了10种图算法, 通过策略模式统一接口。
四套数据库各司其职: Neo4j存图, Redis缓存, MySQL存用户, MongoDB存日志。
```

### ⭐ Q2: 为什么选择 FastAPI 而不是 Flask/Django？
```
FastAPI 的优势:
1. 异步原生支持 (async/await), 适合 I/O 密集型 API 网关
2. 自动生成 OpenAPI 文档 (Swagger UI)
3. Pydantic 数据校验, 类型安全
4. 性能比 Flask 高 2-3x (Starlette 底层)
Django 太重, Flask 缺少异步和自动文档。
```

### Q3: 中间件链的执行顺序是什么？为什么这样排序？
```
CORS → GZip → RateLimit → RequestLog → ErrorHandler → Route

理由:
- CORS 最先: 跨域请求需要在任何处理之前响应 OPTIONS
- GZip 第二: 尽早压缩减少带宽
- RateLimit 第三: 限流在业务逻辑之前
- RequestLog 第四: 记录通过限流的有效请求
- ErrorHandler 最后: 统一捕获所有异常转JSON
```

### ⭐ Q4: C++ 引擎和 Python 之间怎么通信？
```
IPC (进程间通信):
Python 通过 asyncio.create_subprocess_exec 启动 C++ 二进制
→ C++ 从命令行参数读取指令
→ C++ 计算结果, 将 JSON 输出到 stdout
→ 所有日志输出到 stderr (保持 stdout 干净)
→ Python 捕获 stdout, 解析 JSON 返回

为什么不用嵌入调用 (ctypes/pybind)?
→ 进程隔离, C++崩溃不影响Python服务
→ 独立部署, 可以分布到不同机器
→ 60秒超时自动 kill, 安全可靠
```

### Q5: 系统怎么处理数据库不可用的情况？
```
采用 lazy-connect + 优雅降级:
- 启动时不强制连接所有数据库
- 首次请求时建立连接
- 连接失败不崩溃, 标记为 unavailable
- 健康检查实时报告各组件的 healthy/degraded/unavailable 状态
- 核心图计算 (PageRank/社区发现/路径) 不依赖数据库, 纯 C++ 计算可用
```

## 二、算法类

### ⭐ Q6: PageRank 算法的原理是什么？你在项目中怎么实现的？
```
原理: 一个节点的重要性 = 指向它的节点的重要性之和
迭代公式: PR(u) = (1-d)/N + d * Σ(PR(v)/OutDegree(v))

我的实现:
- damping factor d = 0.85
- 默认100次迭代
- 用邻接表存储, 每轮遍历所有边
- 复杂度 O(I * E), I为迭代次数

在 C++ 中用了:
- unordered_map 存储节点分数
- 每轮计算新的分数向量
- 流式模式每轮输出 top-100 (request_handler.h)
```

### ⭐ Q7: LPA 标签传播算法是怎么做社区发现的？
```
原理: 
1. 初始化: 每个节点一个唯一标签
2. 迭代: 每个节点选邻居中出现最多的标签
3. 收敛: 标签不再变化或达到最大迭代次数

我的实现 (AlgoLPA.cpp):
- 最多10次迭代
- 用 unordered_map 统计邻居标签频率
- 遇到平局按字典序选第一个

在你的数据集上: 4039个节点, 50ms完成, 社区数取决于数据。
```

### ⭐ Q8: Dijkstra 和 BFS 找最短路径有什么区别？
```
BFS: 每条边权重为1, 找最少跳数 → O(V+E)
Dijkstra: 每条边有权重, 找最小权重路径 → O((V+E)logV)

我的项目里:
- BFS: 用于找最短朋友链 (经过最少的人)
- Dijkstra: 我伪造了边权重 (哈希取模), 找"最强关系链"
- DFS: 用于检测回声室 (环路检测, 三色标记法)
```

### Q9: 策略模式在你的项目中具体怎么用的？
```
定义了3个抽象接口 (include/Graph.h):

class IPathFindingAlgorithm {
    virtual vector<string> execute(SocialGraph&, string start, string target) = 0;
};
class IScoringAlgorithm {
    virtual map<string, double> execute(SocialGraph&) = 0;
};
class ICommunityAlgorithm {
    virtual map<string, string> execute(SocialGraph&) = 0;
};

每个算法类实现对应接口, main.cpp 通过基类指针调用。
新增算法只需:
1. 创建新类, 继承对应接口
2. 实现 execute 方法
3. 在 main.cpp 注册一个命令

不需要修改任何现有代码 (开闭原则)。
```

### Q10: 你的算法时间复杂度是多少？能处理多大图？
```
当前数据: 4039节点, 88234边

BFS/Dijkstra: 毫秒级
PageRank (5轮): 352ms
LPA (10轮): 53ms
全图拓扑: ~200ms (含网络传输)

理论上限 (单机):
- 邻接表内存占用: O(V+E)
- 100万边, PageRank 100轮 ≈ 30秒
- 分布式改造后可以处理亿级边
```

## 三、数据库类

### ⭐ Q11: 为什么用4种数据库？是不是过度设计？
```
每种数据库有各自的优势场景, 不是堆砌:

Neo4j → 图遍历 (找共同好友、推荐路径) —— 关系型做这个要JOIN几十次
Redis  → 热数据缓存 (PageRank结果用24小时) —— 避免了重复计算
MySQL  → 用户账户 + 事务 (注册/登录/API Key) —— 需要ACID
MongoDB → 操作日志 + 性能指标 —— Schema灵活, 时序数据自然

如果没有这些数据库, 系统也能跑 (降级模式)。
数据库只是让系统更强, 不是必须。
```

### ⭐ Q12: Redis 缓存策略是怎么设计的？
```
统一命名空间: sgp:{domain}:{entity}:{qualifier}
例如: sgp:graph:pagerank:v3

5种失效模式:
1. 版本失效 (主策略) —— 算法升级改版本号 v3→v4
2. 标签失效 —— 批量标记过期
3. TTL兜底 —— 24h自动过期
4. Pub/Sub实时 —— 数据更新推送到所有服务实例
5. Admin API手动 —— /api/v1/admin/cache/invalidate

防击穿: 分布式锁 (Redis SETNX), 只有第一个请求去计算
防雪崩: TTL jitter ±10% 随机偏差
```

### Q13: Neo4j 和 MySQL 都能存数据, 为什么图数据用 Neo4j？
```
考虑"找A和B的共同好友":

MySQL:
SELECT friend_id FROM friendships WHERE user_id = 'A'
INTERSECT
SELECT friend_id FROM friendships WHERE user_id = 'B'
→ 2次索引扫描 + 交集, 数据量大时慢

Neo4j (Cypher):
MATCH (A)-[:KNOWS]->(f)<-[:KNOWS]-(B)
RETURN f
→ 原生图遍历, 只经过相关节点, 更快

图的JOIN在关系型是O(N²), 在图数据库是O(degree)。
```

## 四、前端类

### ⭐ Q14: WebGL 3D 可视化怎么做的？大图不会卡吗？
```
使用 3d-force-graph 库 (基于 Three.js + d3-force):

优化手段:
1. LOD: 近距离球体渲染, 远距离点精灵降级
2. Big Bang渐进展开: 节点分100帧逐步显示, 避免首帧4万节点同屏
3. nodeResolution=16 (降低球体面数)
4. 力导向模拟: cooldownTicks=100, 100轮后停止计算
5. velocityDecay=0.18 (高阻尼快速稳定)

当前数据 (4039节点): 流畅60fps
瓶颈分析: 全量加载4MB JSON, 万级以上需要分页
```

### Q15: Big Bang 渐进展开是怎么实现的？
```
原理:
1. 所有节点按ID排序
2. 分100帧, 每帧分配 (4039/100=40) 个节点
3. 每个节点有 birthFrame 属性
4. 渲染时只显示 birthFrame <= currentFrame 的节点
5. 时间轴滑块控制 currentFrame

效果: 节点从中心逐个"诞生", 视觉上像宇宙大爆炸, 不卡顿。
```

### Q16: 前端零框架是什么意思？为什么不用 React/Vue？
```
零框架 = 不依赖任何前端框架, 用 ES6 原生模块:

好处:
- 无打包构建步骤 (不需要 webpack/vite)
- 浏览器原生支持 import/export
- 项目体积小 (纯 JS 几十KB)
- 学习成本低 (不需要学框架)

代价:
- 大型项目难以维护 (但本项目前端只是可视化层, 不复杂)
- 没有虚拟DOM, 手动DOM操作

适用场景: 本项目前端功能聚焦, 不需要框架的复杂状态管理。
```

## 六、深度追问 (答辩杀手问题)

### Q20: 你的 PageRank 算法是精确的还是近似的？收敛条件是什么？
```
是幂迭代法 (Power Iteration), 数值逼近:

收敛判断:
- 默认固定100次迭代 (不检查收敛)
- 理论上可以加: ||PR_new - PR_old|| < ε 作为停止条件
- ε 通常取 10^-6

为什么不加收敛判断:
1. 图规模可控 (8万边), 100轮很快
2. 固定迭代保证响应时间可预期
3. 如果需要, 加 2 行代码即可
```

### Q21: 如果让你把 C++ 引擎改成分布式, 你会怎么做？
```
方案一: MPI 并行
- 按节点分区, 每台机器持有部分节点和邻接边
- PageRank 每轮需要边界通信 (ghost node scores)

方案二: Pregel 模型
- 以节点为中心, 节点向邻居发消息
- 适合迭代图算法

方案三: 简单分区
- 不同算法跑在不同机器
- 用消息队列分发任务

对于本项目, 方案三最实际。
```

### Q22: 你的 MongoDB 索引创建失败是怎么回事？
```
日志中有 WARNING: "partialFilterExpression must be an object, but got null"

这是代码中传了 null 给 MongoDB 的 partialFilterExpression 字段。
MongoDB 不接受 null, 需要要么不传这个字段, 要么传一个对象。
这不是功能问题, 索引本身会创建, 只是部分索引的过滤器没生效。

修复: 在 Python 代码中过滤掉 null 值再传给 MongoDB。
```

### Q23: BaseSettings 的 env_prefix 和手动 override 有什么区别？
```
env_prefix = "SGP_" → Pydantic 自动读取 SGP_REDIS_HOST 等
手动 override → 兼容旧环境变量 (REDIS_HOST 等非前缀版本)

优先级: init_settings > env_settings (带前缀) > file_secret_settings
手动 override 在 get_settings() 中执行, 覆盖已加载的 settings

这是向后兼容设计, 让 docker-compose.yml 中的变量名不用改。
```

### Q24: 前端的 3d-force-graph 库如果断网了怎么办？

```
当前: CDN 加载 unpkg.com 上的脚本, 断网无法加载。

改进方案:
1. 本地托管: npm install 3d-force-graph, 放到前端目录
2. Service Worker: 离线缓存

实际答辩场景: 离线演示建议提前确保网络, 或提前打开浏览器缓存。
```

### Q25: 你的系统有什么安全措施？
```
1. JWT 认证: Access Token 15min + Refresh Token 30天
2. API Key: SHA-256 哈希存储, sk_ 前缀
3. 三层限流: 匿名10/登录60/API Key 300 每分钟
4. bcrypt: cost=12 密码哈希
5. CORS: 只允许配置的域名
6. 错误隐藏: 生产环境不暴露堆栈
7. SQL注入防护: 参数化查询 (SQLAlchemy/aiomysql)
```

## 七、"如果...怎么办"类问题

### Q26: 如果数据量扩大100倍 (400万节点, 8千万边), 你的系统还能跑吗？
```
前端: 全量加载不可行, 需要:
- 后端分页/分块返回
- 前端视锥裁剪 (只渲染可见节点)
- LOD 更激进

后端: 
- C++ 引擎需要分布式改造
- Neo4j 需要集群模式
- Redis 集群分片

MySQL/MongoDB: 当前设计可以支撑, 加索引即可
```

### Q27: 如果你的 C++ 引擎进程崩溃了怎么办？
```
当前处理:
1. Python 的 subprocess.run 有 60 秒超时
2. 进程崩溃 → Python 捕获异常 → 返回 500 错误
3. 不会拖垮 API 服务 (进程隔离的好处)

改进方案:
- 进程池 (pool_size=4): 预启动4个引擎进程
- 健康检查: 定期 ping, 挂了的自动重启
- 请求重试: 换个进程重试
```
